# Instructions for the AI agent

You build a small **static web page** and deploy it on the Nutanix Kubernetes
Platform (NKP) by following the platform's rules. People are watching a live
dashboard: every step you take must be visible there. Follow this procedure
**exactly, in order**. Do not improvise other commands.

## Your tools (the ONLY commands you may run)

The platform team provides the `vibe` command line tool:

| Command | When |
|---|---|
| `vibe status coding` | FIRST, before writing any code |
| `vibe images "<subject in English>" --count 3` | to get real photos for the page |
| `vibe validate` | after filling `contract.yaml` |
| `vibe push "<message>"` | after the user confirmed |
| `vibe diag --wait` | right after the push |
| `vibe diag` | any time, to see the current status |
| `vibe raz -y` | ONLY when the user explicitly asks to reset the demo |

Never run `git`, `kubectl`, `docker`, `curl` or any other command yourself.

## Files you may change

* `app/` - the web page: `index.html`, any `.css`/`.js`, and the photos in
  `app/images/` (downloaded with `vibe images`). Static files only.
  Keep `app/Dockerfile` as is.
* `contract.yaml` - the platform contract. Rules in `CONTRACT.md`.

Never edit `deploy/` (generated by the platform), `.github/`, `AGENTS.md`,
`CONTRACT.md`, `opencode.json`.

## Procedure

1. **Announce** - run `vibe status coding`.
2. **Build the page** - write `app/index.html` (inline CSS/JS is fine, no build
   step, no framework that needs npm). It must work when opened directly as a file.
   Make it look professional: a hero section, real photos, clean typography.
   * **Images**: run `vibe images "<subject in English>" --count 3` **once**
     (twice at most, with another subject). It downloads free photos into
     `app/images/` and prints the `<img>` tags to use and a credits line:
     put the credits line in the page footer.
   * Never invent image URLs and never link images from other websites.
   * If it prints `NO IMAGES`, continue without photos (CSS gradients, emoji).
3. **Fill the contract** - read `CONTRACT.md`, then update `contract.yaml`:
   * Keep `app: vibe-app` unless the user explicitly asks for another name.
   * Keep `port: 8080` (the nginx template listens on 8080).
   * For every field you cannot decide from the request, **ask the user in
     simple words** (use the questions in CONTRACT.md). One short question at a time.
4. **Validate** - run `vibe validate`. If it prints `CONTRACT REFUSED`, fix
   `contract.yaml` (ask the user if the fix needs a decision) and run it again.
5. **Confirm** - show the user the summary printed by `vibe validate` and a
   one-line description of the page. Ask: "Shall I deploy?" Wait for a yes.
6. **Push** - run `vibe push "<short description of the change>"`.
7. **Follow** - run `vibe diag --wait`. It prints each step as it progresses.
   * Exit 0, `DEPLOYED: <url>` -> tell the user the app is live and give the URL.
   * `STILL RUNNING` -> nothing is wrong, run `vibe diag --wait` again.
   * `FAILED at step ...` -> read the reason. If it is about the contract or the
     page, fix it, go back to step 4. If it is an infrastructure error, explain
     it simply to the user and stop.
8. **Stop** - do nothing else unless the user asks.

## Resetting the demo

Only when the user explicitly asks to reset the demo ("reset", "RAZ",
"start over"): run `vibe raz -y`, then answer "Demo reset - ready for the next
request." Never run it on your own initiative. After a reset, start the next
request again from step 1.

## Style

Short messages. Explain platform choices in plain words, no Kubernetes jargon
unless the user asks.
